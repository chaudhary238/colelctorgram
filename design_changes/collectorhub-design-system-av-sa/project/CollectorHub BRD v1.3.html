Section 1

Document Control & Purpose

This Business Requirements Document (BRD) defines the product vision, scope, functional requirements, and phased delivery plan for CollectorHub — a community-oriented social platform for hobby collectors. It is intended to align the product, engineering, content, and marketing workstreams on what we are building, for whom, in what order, and how success will be measured.

The document is deliberately phased. Phase 1 targets an initial community of 10,000 engaged users across four collectible categories; Phase 2 expands categories, monetisation, and platform depth once retention and liquidity are proven.

1.1 Intended Audience

Engineering / build team (RC) — to scope and sequence the application build.
Content & Marketing (SA, AV) — to plan seeding, content calendars, and go-to-market.
Founders / stakeholders — to confirm scope, priorities, and the phasing decision.

Section 2

Executive Summary

Collecting is a large, fast-growing, and deeply social hobby — yet collectors today are scattered across general-purpose tools: Instagram for showcasing, WhatsApp and Facebook Groups for community and buy/sell/trade, eBay and marketplace apps for transactions, and Discord/Reddit for discussion. No single product combines identity, community, discovery, and trusted peer-to-peer trading in one place tuned to a collector's specific interests.

CollectorHub closes that gap. A collector creates a profile, selects their interests, and builds a collection portfolio — adding items quickly from a built-in catalogue (search or barcode scan) and confirming what they actually own with an in-app photo. Any owned item can be listed for sale or trade in a tap; pre-orders carry a value and timeline. A personalised master feed surfaces new releases, community discussions, marketplace listings, events, and ISO (In Search Of) posts relevant to them. They join communities, message other collectors directly to transact, confirm completed deals, and build reputation through transaction-linked trust signals.

Phase 1 launches with four categories — Action Figures, Designer Toys & Blind Boxes, Model Kits & Lego, and Diecast — and a target of 10,000 engaged users.

9.3 Master Feed (Home) Updated

Purpose. The daily destination: a personalised stream that gives every user a reason to return multiple times a day.

✏️
Changes from v1.2: (1) ISO posts are now a card type in the feed. (2) @mentions in comments are tappable and navigate to the tagged user's profile. (3) The ISO Board is removed from Marketplace — ISO surfaces here only.

Key components & features

Ranked 'For You' feed from interests + follows + behaviour. Sort control (For You / Latest / Top). Filter control (category/interest, post type, source). Decision: listings appear in the feed by default; a 'hide listings' filter lets users opt out.

Mixed cards: user posts (Showcase / Discussion / Review / ISO), admin news/releases, joined-community posts, listing announcement cards, event cards.

Per-card author with a Follow button; trust indicator, post-type tag. Quick actions (like, comment, save, share, message). For ISO cards, an additional "I have this" CTA opens a DM to the poster. Comments expand inline within the feed. Pull-to-refresh; infinite scroll.

✨
New — ISO feed card: Displays item name, budget, condition, optional reference images, and "I have this" button. Like, comment, bookmark, and share actions are on the left — consistent with all other card types. The "I have this" button sits on the right as the primary CTA.
✨
New — @mention navigation: @handles in comment bodies are rendered as tappable links. Tapping an @mention navigates to that user's profile. This applies to all post types and their comment threads.

Action alignment rule

All post card action rows (like, comment, bookmark, share) are left-aligned across every post type — Showcase, Discussion, Review, and ISO. Secondary CTAs (e.g. "I have this" on ISO) are right-aligned in the same row. This is a hard UI rule; no card type may deviate.

Phase

P1: interest + behaviour ranking, sort/filter, in-feed follow, inline comments, hide-listings filter, ISO feed cards, @mention navigation. P2: ML ranking, trending, digests.

9.6 Post Composer Updated

Purpose. Let users contribute social content quickly. (Selling is NOT here — it is an action on a collection item, §9.5.)

✏️
Change from v1.2: ISO added as a post type in the composer's post-type selector. The ISO compose surface adds specific fields: item name/description, budget (optional), condition preference (optional), and reference image upload (gallery or camera, no in-app-live-capture requirement).

Key components & features

Post-type selector is the first action when the user taps 'New post': Showcase / Discussion (Question) / Review / ISO / Poll. Single compose surface — text with optional image(s). ISO-specific fields: item being hunted, budget, preferred condition. Poll option: question + multiple answer choices. Optional 'reference an item/listing' picker. Interest/category tags; optional community selector. Image picker/camera with crop.

States & edge cases

ISO post with no item name → block publish. Oversized/invalid image → client-side check. Poll with fewer than two choices → block publish. Deleting a post does not delete the referenced item/listing. Draft loss on exit → confirm prompt.

Phase

P1: post-type-first composer (Showcase / Discussion / Review / ISO / Poll) + optional reference images + item reference. P2: carousels, video, drafts/scheduling, ratings.

9.8 Marketplace (Browse) Updated

Purpose. A trusted place to discover items for sale or trade, tuned to the user's interests.

🗑️
Removed from v1.2: The ISO Board tab has been removed from the Marketplace screen. ISO posts are not a marketplace construct — they are social content expressing demand, not supply. Surfacing them in a supply-side marketplace created a category mismatch and a confusing IA. ISO posts live in the Feed only (§9.3, §8.5 PO-02b). See §19.1 for full reasoning.

Key components & features

Listing grid/list (Listings created from collection items, §9.5). Search bar; filters: category, price range, condition, location, trade-only. Sort: newest, price, relevance. Listing cards: image, title, price, condition, seller trust signal. Saved searches / watchlist; wishlist-match entry point.

Primary user actions

Search, filter, sort. Open listing detail. Save/watch a listing or save a search. Jump to seller profile.

States & edge cases

No results → suggest broader filters. Sold/closed listing → hidden/labelled. Location not set → prompt or default region.

Phase

P1: browse, search, filter, save + wishlist match. P2: offers/bidding, condition standards, in-app checkout.

Section 19 — New in v1.3

Reasoning for v1.3 Changes

This section documents why v1.3 departs from v1.2. Each change is stated as Problem → Change → Why, following the pattern established in §18.

19.1 ISO moved from Marketplace board to Feed post type

Problem. v1.2 added an "ISO Board" tab inside the Marketplace screen. ISO posts are an expression of demand (I am looking for X), not a supply listing (I am selling X). Placing demand-side content inside a supply-side screen (the Marketplace) created a category mismatch, confused the information architecture, and split ISO post visibility away from the main feed where most engagement happens.

Change. ISO is now a post type in the composer (alongside Showcase / Discussion / Review / Poll) and surfaces as a card type in the master feed. The Marketplace ISO Board tab has been removed entirely. See §8.5, §9.3, §9.6, §9.8.

Why. Feed placement gives ISO posts the same organic reach as any other post type — followers see them, they appear in filtered views, and they are discoverable via search. The "I have this" CTA on ISO cards directly routes supply (a holder) to demand (the poster) via DM, which is the correct transaction path. Keeping it in the feed avoids a second IA destination for what is fundamentally social content expressing intent.

19.2 DM attachment sheet made functional

Problem. The + (attach) button in DM threads existed in the design but showed only a toast with no action. This was a gap between the specified capability (DM-03: attach items as trade offers) and the built state.

Change. The + button now opens a bottom sheet with three concrete options: Photo, Share listing, and Make offer. See §8.7 DM-03 and §9.10.

Why. The Make offer flow — with the listing price pre-filled and editable — is a direct enabler of the DM-to-Deal conversion funnel (§14). Photo and Share listing cover the two most common supplementary needs in a buy/sell negotiation. Defining these as discrete options (rather than a freeform attachment picker) keeps the action surface simple and intent-clear.

19.3 @mention navigation in comments

Problem. @handles in comment bodies were rendered as styled text but were not interactive. Users expected tapping a mention to navigate to that profile — a near-universal convention — and the missing behaviour was a noticeable friction point.

Change. @mentions in all comment bodies are now tappable and navigate to the mentioned user's profile. See §9.3.

Why. This is table-stakes social UX. It also increases profile discovery and follow rates, feeding the follow graph that drives feed personalisation (§8.4 FE-02).

19.4 Opt-in public DM threads removed; replaced by Listing Q&A

Problem. v1.2 §9.10 specified that both parties in a DM thread could opt in to make the conversation public on the listing post. This feature had four unresolved problems:

  1. No defined display surface. Where would the public thread appear? The listing page? A community feed? The screen spec did not resolve this, making implementation undefined.
  2. Unilateral consent risk. The toggle was surfaced only on the buyer's side. The seller had no prior opt-in; only the mutual-opt-in state was safe, but the UX made the first opt-in feel like it worked immediately — a potential privacy leak.
  3. Content contamination. A DM thread initiated for price negotiation might contain personal details, lowball offers, or location information that should not become public. The only safeguard was user discipline, which is not a safeguard.
  4. Storage and moderation complexity. Public threads derived from private DMs require a separate public content store, moderation hooks, and a display surface — a non-trivial scope addition relative to the value delivered.

Change. The "Make thread public" toggle is removed from DM threads entirely. DMs are always private. A new Listing Q&A block (§9.9, LD-10) is added to the Listing Detail page: any viewer can ask a question; only the seller can answer; all content is always public. See §9.9 and §9.10.

Why. The Listing Q&A block delivers the legitimate value of public DMs (other buyers see common questions answered, reducing repeat DMs to the seller) without the privacy, consent, and implementation problems. It is structured from the start as public content — there is no leakage from private to public because the channel is separate and opt-in is not required (questions are always public by design, which users understand before typing).

19.5 UI alignment rules codified

Problem. During build review, several screens showed text wrapping or overflow when user names, tier badges, follower counts, or timestamps appeared together in constrained flex rows — causing misalignment (e.g. a name badge pushing onto a second line).

Change. A set of layout rules is now codified for all name/badge/count/timestamp rows throughout the app: (a) name spans get whiteSpace: nowrap; overflow: hidden; textOverflow: ellipsis; minWidth: 0; flexShrink: 1; (b) tier chips and timestamps get flexShrink: 0; whiteSpace: nowrap; (c) the containing flex row gets overflow: hidden. These rules apply in AuthorLine, CommentRow, ChatInboxRow, ListingSellerCard, and any future name-badge-time pattern.

Why. Overflow and wrapping bugs appear only at edge cases (long names, many badges, small viewports) and are easy to miss during primary-path testing. Codifying the pattern as a rule — rather than fixing each instance individually — prevents recurrence as new screens are built.
